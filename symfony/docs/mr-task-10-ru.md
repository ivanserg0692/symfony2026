## Обзор

Этот документ описывает планируемый результат merge request для Task 10.

Merge request: [PR #14](https://github.com/ivanserg0692/symfony2026/pull/14)

Файл задачи: [task-10.md](task-10.md)

Планируемый merge request внедряет Elasticsearch read-модель каталога для полнотекстового поиска, тяжёлой фильтрации, точного `COUNT`, фасетов и агрегаций по каталогу примерно из 1 млн товаров. Работа продолжает исследование производительности из Task 9, где эти операции PostgreSQL были определены как основной оставшийся bottleneck каталога.

PostgreSQL остаётся единственным источником истины и хранилищем для операций записи. Elasticsearch содержит версионируемую денормализованную eventually consistent проекцию, оптимизированную для чтения каталога и производных поисковых структур; он не заменяет транзакционное хранилище и не становится универсальным кешем приложения.

## Scope

Планируется:

- добавить Elasticsearch как отдельный инфраструктурный read-компонент Catalog Service;
- определить versioned mapping, settings, analyzers, normalizers, aliases и схему поискового документа;
- реализовать идемпотентную первичную индексацию примерно 1 млн товаров с контролем прогресса и безопасным повторным запуском;
- реализовать надёжную инкрементальную синхронизацию создания, изменения и удаления товаров;
- предусмотреть retry, обработку ошибочных событий, replay, мониторинг synchronization lag и процедуры восстановления;
- перенести в read-модель полнотекстовый поиск, фильтрацию, сортировку, пагинацию, точный подсчёт результатов, фасеты и необходимые агрегации;
- обеспечить безопасную полную переиндексацию в новую версию индекса с атомарным переключением alias и rollback;
- сравнить производительность Elasticsearch с воспроизводимым PostgreSQL baseline на одинаковых данных, оборудовании и профиле нагрузки;
- задокументировать индексацию, reindex, диагностику, rollback и восстановление после сбоев.

## Архитектурные решения

- PostgreSQL хранит канонические товары, связи и транзакционные данные.
- Elasticsearch хранит денормализованную проекцию для явно поддерживаемых сценариев чтения каталога.
- Catalog Service владеет поисковым контрактом и не раскрывает Elasticsearch DSL клиентам API.
- Запись товаров не должна зависеть от синхронной двойной записи в PostgreSQL и Elasticsearch.
- Изменения доставляются асинхронно через надёжный event pipeline; transactional outbox является предпочтительным направлением и должен быть подтверждён при проектировании интеграции.
- Mapping индекса, формат документа и интеграционные события версионируются.
- Eventual consistency допускается только в пределах определённого, измеряемого и наблюдаемого окна.
- Elasticsearch нельзя использовать для транзакционных проверок остатков, цены заказа и других strongly consistent операций.

## Фильтрация и пресеты

- Определить allowlist публичных полей фильтрации, операторов, сортировок и лимитов.
- Поддержать точное совпадение, множественный выбор, диапазоны, проверку наличия значения и безопасные комбинации разрешённых условий.
- Оставить имена полей Elasticsearch и query DSL внутри infrastructure-адаптера.
- Добавить версионируемые системные именованные пресеты для типовых комбинаций фильтров, сортировки и поисковых параметров.
- Определить однозначные правила приоритета между пресетом и явными параметрами запроса.
- Валидировать пресеты и исключить хранение или выполнение произвольного клиентского Elasticsearch DSL.

## Проверка производительности

PostgreSQL baseline и результат Elasticsearch должны измеряться на одинаковом dataset примерно из 1 млн товаров, оборудовании, конфигурации контейнеров, процедуре прогрева и профиле нагрузки.

Фиксируются:

- RPS и error rate;
- p50, p95 и p99 latency;
- снижение нагрузки на PostgreSQL;
- CPU, RAM, storage, размер индекса и search latency Elasticsearch;
- длительность индексации и переиндексации;
- synchronization lag и количество ошибочных событий;
- функциональная эквивалентность поиска, фильтров, подсчётов, фасетов и агрегаций в пределах заявленного consistency window.

## План проверки

Реализацию нужно проверить по следующим признакам:

- первичная индексация является полной, наблюдаемой, идемпотентной и безопасно перезапускаемой;
- события создания, изменения и удаления товара корректно обновляют read-модель;
- повторные, задержанные и переотправленные события не повреждают данные индекса;
- новую версию индекса можно построить, проверить, активировать через alias и откатить;
- недоступность Elasticsearch обрабатывается контролируемо и заметно, без незаметной выдачи некорректных результатов;
- неподдерживаемые поля, операторы, сортировки и чрезмерные лимиты отклоняются контрактом приложения;
- каждый системный пресет валидируется и объединяется с явными параметрами по документированным правилам;
- результаты Elasticsearch соответствуют каноническим данным PostgreSQL в пределах заявленного окна eventual consistency;
- существующие сценарии каталога, API Gateway, Cart Service и Order Service остаются работоспособными;
- повторные нагрузочные тесты показывают измеримое улучшение p95 для согласованных тяжёлых поисковых сценариев и снижение нагрузки на PostgreSQL.

## Вне Scope

- замена PostgreSQL как источника истины или write-хранилища;
- синхронная двойная запись как механизм консистентности;
- публикация произвольного Elasticsearch DSL через публичный API;
- использование Elasticsearch для транзакционных проверок остатков или цены заказа;
- персональные сохранённые фильтры пользователей;
- рекомендации, персонализация, autocomplete, typo tolerance, semantic/vector search и сложное ранжирование без отдельного согласования;
- несвязанные изменения бизнес-логики, API или архитектуры.
